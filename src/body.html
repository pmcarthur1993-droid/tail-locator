Developer notes — where the data comes from and how a result is verified

    

      
Pipeline

      

        
1 · IdentityRegistration → Mode S hex, type, operator (adsbdb.com, fallback hexdb.io).

        
2 · Live positionadsb.lol, airplanes.live, adsb.fi by registration and by hex; OpenSky by hex. All queried, every time.

        
3 · Historyadsb.lol per-aircraft trace: today's rolling file, then the daily archive back up to 14 days.

        
4 · Airport matchFreshest fix → nearest airport from the embedded OurAirports database, runway-derived boundary.

        
5 · VerificationSeven checks on the ground, seven in flight. All must pass or the line is withheld.

        
6 · OutputCODE - Airport - Country, or Currently en route to … from …, or UNVERIFIED - manual check required - reason.

How the fix is chosen

      
    
        
  1. Every live source is queried; each returns at most one fix per aircraft with its own age. The freshest fix wins; the others are kept for the "Sources agree" check.
    2. 
        
  2. If no live fix is fresher than 15 minutes, or the aircraft is airborne, the adsb.lol trace is read. Its last point becomes the fix if it is newer than anything live. The trace walk starts with today's rolling file and steps back one archive day at a time until a file exists (look-back setting, default 7 days, max 14).
    3. 
        
  3. On-ground means the transponder's ground flag, or altitude within 1,500 ft of field elevation at ≤ 60 kt with no significant vertical rate. Anything else is airborne.
    4. 
        
  4. On the ground, the airport is the nearest one whose boundary contains the fix. When two boundaries overlap, the larger airport is preferred (a GA field inside a major's footprint does not win).
    5. 
        
  5. In flight, the destination is the filed one (FR24, if used) or the callsign's usual route; the departure is where the current leg's last ground point was in the trace. The schedule is never used to place the aircraft.
    6. 
        
  6. Diversions: only FR24's flight record (dest_iata_actual differing from dest_iata) is treated as a confirmed diversion. A landing somewhere other than a community route database's usual destination is noted as information only — usual routes are not filed plans. On the ground the output is always where the aircraft physically is, so a diversion never changes the line.
    7.

Coverage
The community feeds depend on volunteer receivers. Coverage is dense over Europe, North America, Japan, Australia and most of Asia-Pacific, and thin or absent over mainland China, much of Africa, Central Asia and the oceans — an aircraft there shows as "track lost" or "not seen". The FlightAware record closes that gap for arrivals and departures (not live position). The Lookup tab and /locate use the server engine, which includes FlightAware; the Full detail tab is the browser's own view of the free feeds.

      
What verification cannot do
It cannot see what no receiver heard. An aircraft towed with its transponder off, parked at a field with no ADS-B coverage, or flying outside coverage is reported as UNVERIFIED, never guessed. Treat the output as surveillance evidence, not an operator statement.

Files, storage and limits

      
    
        
  • Tail-Locator.html — this page, self-contained; airport and country data embedded. tail_locator.py — launcher, relay and lookup engine (Python 3.8+, standard library only). airports.json — the same data for the Python engine. Start-Tail-Locator.bat — Windows launcher. tail-relay-worker.js — optional Cloudflare relay for use where the launcher is not running.
    • 
        
  • Browser storage holds only settings, the last 12 registrations, and 30-day caches of identity/route lookups. Nothing is sent anywhere except the API calls listed.
    • 
        
  • Rate limits respected: 1 request/second per aggregator, OpenSky anonymous daily quota, traces fetched sequentially. A lookup for a parked aircraft typically makes 8–12 requests and takes 5–15 seconds; trace files can be 0.5–1 MB each.
    • 
        
  • Page and engine are tested against mocked API responses (47 browser cases, 17 engine cases) covering FR24-recorded diversions, reused callsigns, identity mismatches, single uncorroborated fixes and off-airport positions.

Registry, routes & display

        
Always on, no key: identity from adsbdb.com and hexdb.io, usual routes for a callsign from adsbdb / hexdb / VRS standing data, photo from planespotters.net. Airport database: OurAirports, 9,765 airports with runway-derived boundaries, embedded in this file.

        
        
Nothing leaves this browser except the API calls themselves. Settings and the last 12 lookups are kept in this browser's local storage.

      

      

        
Flightradar24 API optional · paid active

        
Not required. A subscriber key adds FR24's filed routes and its flight history with the recorded actual arrival airport, which then take part in verification. Explorer plan is $9/month for 30,000 credits; a lookup costs about 8–30. Leave empty to stay on free data.
